| Q14 | Seed script  | OPEN   | `make seed` is defined per AGENTS.md but no seed dataset was specified. ASSUMPTION: target and content pending owner decision; the Makefile target fails with a pointer until defined. |
| Q15 | Reminder proposal durability | OPEN | ASSUMPTION: unconfirmed reminder proposals, the "type a new time" wait and the `/verilerimi_sil` confirmation are held in bounded in-process stores (same pattern as password entry state). A restart silently drops them; nothing half-typed is ever written to PostgreSQL. Persist proposals if restarts must survive them. |
| Q16 | Failed reminder delivery | OPEN | ASSUMPTION: after three outbox send attempts the delivery row terminates in `FAILED` and the reminder stays `PAUSED` (never re-claimed, because `(reminder_id, scheduled_for)` is unique). No operator alert or manual retry UI exists yet. Decide whether to notify admins or allow a retry command. |
| Q17 | Timezone capture | OPEN | SPEC §4.1 says `/start` asks for the timezone. ASSUMPTION: V1 stores the `Asia/Baku` server default for every account and never asks, because all known users are in Azerbaijan and the auth flow stays one step. Reminder times are therefore Baku-local. Add a follow-up prompt (or a `/saatqusagi` command) if any user needs a different zone. |
| Q18 | Web freshness vocabulary | PARTLY ANSWERED | ASSUMPTION: `is_fresh_query` accepts only an explicit right-now wording (`indi`, `hazırda`, `bu gün`, `son xəbər`, `latest`, `current`, `today`, `news`), while `is_time_sensitive_query` separately marks volatile subjects (`qiymət`, `qiymətlər`, `stok`, `satış`, `kurs`) that only need a short cache TTL. A fresh query returning nothing is retried once without a time window before the user is told nothing was found. SPEC is silent on all of this; confirm the vocabulary with real usage before widening it. *Answered part (Block 4, 2026-10-07):* the window is now enforced against the result, not only requested of the engine — a hit carrying its own publication date outside the window is not usable, and an undated hit stays, because SearXNG supplies `publishedDate` for almost nothing and absence of a date is not proof of age. The vocabulary itself is still OPEN. |
| Q19 | Vision cost and limits | OPEN | ASSUMPTION (revised 2026-10-07): nothing is sent to a vision vendor at upload. One call happens per image per turn that asks about it, with `gpt-4o-mini` and a byte bound well below `max_upload_bytes`; there is no cache of transcriptions, no daily cap, no per-user budget and no cost tracking, so a repeated question repeats the call. SPEC is silent. Decide whether to cache image text and add a budget before image questions become common. |
| Q20 | Vision text and business facts | OPEN | ASSUMPTION: image text read on demand is untrusted query/context material only. It is never a citation of a company source, `extraction/sources.py` keeps skipping runs flagged `requires_vision`, and a price read off a photo can never become a business fact without the candidate-first human review or the explicit `/saxla`-style confirmation in Phase 12A. Confirm whether photos should ever feed structured extraction directly. |
| Q21 | Qdrant read target | OPEN | ASSUMPTION: reads resolve the live projection per query (alias first, then the physical collection name) and the application never creates or re-points an alias, because only the worker publishes it during indexing. SPEC §12 is silent about who may repair alias state. Confirm whether the app may re-create a lost alias, or whether a lost alias should page an operator instead of silently reading the physical collection. |
| Q22 | Clarification wording | OPEN | ASSUMPTION: only reason codes with a known missing element get targeted Azerbaijani text (`customer_required_for_proposal_comparison` → ask for the customer); every other clarification, including anything the LLM planner labels itself, gets one neutral wording that names no entity. Master Spec §3.8 requires clarification but is silent about its text, and the code catalog rule is already relaxed inside `internal_evidence`. Confirm the per-intent clarifications (product, document, date range) once real usage shows which ones recur. |
| Q23 | `/internet` and attached pictures | ANSWERED | DECISION (owner, 2026-10-07, Block 4 clearance): `/internet` alone does not read a picture attached to the caption, because there is no internal evidence to combine it with and sending text read off a company photo to a public search engine is avoidable egress. `/tamaxtar` (combined) does read it, and `/baza` reads it as a query parameter. The caption is still routed, so the command is never silently dropped; the user is told the file was not stored. Master Spec §22 requires that media not be discarded but is silent about which web mode reads it. Revisit only if the owner withdraws this decision. |
| Q24 | Startup clock validation strength | OPEN | ASSUMPTION: a process clock that differs from PostgreSQL `now()` by more than `CLOCK_DRIFT_WARNING_SECONDS` (120) logs one WARNING and the process serves anyway, because invariant 8 forbids an infrastructure diagnostic from taking the bot offline and a single measurement cannot say which of the two clocks is wrong. SPEC is silent on enforcement. Confirm whether a large skew should instead refuse to start the reminder dispatcher in `workers/ingestion.py`, which is the only component that writes deadlines. |
| Q25 | Proof of freshness for undated hits | OPEN | ASSUMPTION (Block 4, 2026-10-07): inside a requested time window a hit is dropped when its own `published_at` falls outside it, but an undated hit is kept — absence of a date is not proof of age. Live check against the local SearXNG: 0 of 6 hits carried a `publishedDate`, so the day window is in practice enforced by SearXNG's `time_range` parameter and not by this service. That means a `bu gün` answer can rest on a page whose age we cannot see. Confirm whether an explicit freshness request should instead require a dated hit, which would empty most day-window answers. |
| Q26 | Image asset orphan content files | OPEN | ASSUMPTION (Block 5A, 2026-10-08): registration copies bytes into `image_assets/` before the row commits, so a crash between the two leaves a file no row names; and because `image_asset_occurrences` cascade with their source document while `image_assets` deliberately has no parent, an asset whose last occurrence is deleted keeps its row and its bytes. Nothing sweeps either case yet. Confirm whether a reconciliation sweep belongs in the worker or in `make` maintenance. |
| Q27 | Second copy of an uploaded photo | ANSWERED | Owner decision (2026-10-09): a standalone JPEG/PNG upload keeps both paths - `blobs/` holds the inviolable original the user sent, and `image_assets/<digest>` holds the internal resource that image search and product relations point at. Chosen so that pruning either namespace later cannot destroy what the other depends on; the disk cost of the second copy is accepted. No change needed. |
| Q28 | Formats whose size can be read | PARTLY ANSWERED | ASSUMPTION (Block 5A, 2026-10-08): dimensions come from the PNG `IHDR` chunk and the JPEG start-of-frame marker, read by hand because Pillow is not a dependency and adding one needs a decision of its own (no ADR covers imaging libraries). A JPEG that carries no frame marker is registered with `width`/`height` NULL rather than a guess. Still OPEN: HEIC/WebP from phones, which are rejected today as they were before (see Q2). |
| Q29 | Embedded picture limits | OPEN | ASSUMPTION (Block 5B, 2026-10-08): a document yields at most `MAX_EMBEDDED_IMAGES_PER_DOCUMENT` (200) pictures and none larger than `MAX_EMBEDDED_IMAGE_BYTES` (8 MiB); both bounds are chosen to keep one parse run inside the worker's memory, and Master Spec §23 gives no numbers. A payload over either bound is counted and named in the run's warnings instead of being kept or silently lost. Confirm the figures against a real corpus page, or make them settings. |
| Q30 | Embedded pictures this build declines | PARTLY ANSWERED | ASSUMPTION (Block 5B, 2026-10-08, widened the same day): a flat PDF raster is now stored, not refused - `processing/pdf_images.py` rebuilds `/FlateDecode`, `/LZWDecode`, `/RunLengthDecode` and unfiltered 8-bit DeviceGray/DeviceRGB grids into a PNG over the dictionary's own `/Width` x `/Height`, and carries a `/SMask` as the alpha channel it describes. What is still reported and not stored, each named in the run's warnings: a PDF inline image (`BI ... ID`), which would have to be cut out of the content stream; `/JPXDecode`, whose bytes travel as they arrive but no header reader here describes JPEG 2000; any other stream filter (CCITT, JBIG2, DCT with a chain); a colour space with no rule here (`/Indexed`, `/Separation`, `/DeviceN`, `/DeviceCMYK`), a bit depth other than 8, a `/Decode` or `/Mask` standing between samples and painted colour, a stencil `/ImageMask`, a declared grid the bytes do not fill, and a `/SMask` that cannot be reconciled with its picture (a JPEG keeps its own bytes, so its mask is named, not folded in). DOCX is now read beyond the body: a picture inside a header or footer a section defines is sighted at that part and role (`word/header1.xml`, `default_header`), while a section that links its header to the previous one owns no definition and invents nothing. What DOCX still does not sight: footnotes, endnotes and comments parts, and a legacy VML `v:imagedata` reference, which carries no `a:blip` to follow. Confirm whether Phase 12B widens any of these. |
| Q31 | Confirming a picture before `/saxla` | OPEN | ASSUMPTION (Block 5C, 2026-10-09): the caption `Bu KA45-dir, yadda saxla` is itself the explicit human confirmation (§22.3's five steps are satisfied by the words the user typed, so there is no proposed action awaiting approval and nothing for `/cancel` to revoke). It therefore lands while the upload session is still OPEN: the relation and its `image_assets/` copy exist before `/saxla` commits the session, and if the user then cancels, the staged blob is deleted while the confirmed content and relation stay — which is the isolation Q27 was decided for. Nothing in this build makes the caption commit the session. Confirm (a) whether the naming caption should also commit it, and (b) whether a revoke command is needed for a confirmation the user changes their mind about. |
| Q32 | What counts as a naming caption | OPEN | ASSUMPTION (Block 5C, 2026-10-09): `business/reference_confirmation.py` recognizes exactly one shape — a caption that ends with `yadda saxla` and names one token that contains a digit, with an Azerbaijani copula (`-dir/-dır/-dur/-dür/-dər`, and the clipped `-dı/-di`) stripped from it. So `Bu KA45-dir, yadda saxla` confirms, `Bu şəkli yadda saxla` (no code), `Bu KA45-dir, yadda saxlama` (negated), `yadda saxla, bu KA45-dir` (phrase not closing) and `Bu KA45-dir, KA46 deyil, yadda saxla` (two names) write nothing. A digit is required because otherwise an ordinary word becomes an identity claim (invariant 1). Only photos are covered: a document caption carrying the phrase stays an ordinary instruction. Confirm the vocabulary and whether documents and other phrasings ("bu məhsul KA45", "KA45 şəkilini saxla") should be read too. |
