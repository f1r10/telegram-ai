| Q30 | Embedded pictures this build declines | PARTLY ANSWERED | ASSUMPTION (Block 5B, 2026-10-08, widened the same day): a flat PDF raster is now stored, not refused - `processing/pdf_images.py` rebuilds `/FlateDecode`, `/LZWDecode`, `/RunLengthDecode` and unfiltered 8-bit DeviceGray/DeviceRGB grids into a PNG over the dictionary's own `/Width` x `/Height`, and carries a `/SMask` as the alpha channel it describes. What is still reported and not stored, each named in the run's warnings: a PDF inline image (`BI ... ID`), which would have to be cut out of the content stream; `/JPXDecode`, whose bytes travel as they arrive but no header reader here describes JPEG 2000; any other stream filter (CCITT, JBIG2, DCT with a chain); a colour space with no rule here (`/Indexed`, `/Separation`, `/DeviceN`, `/DeviceCMYK`), a bit depth other than 8, a `/Decode` or `/Mask` standing between samples and painted colour, a stencil `/ImageMask`, a declared grid the bytes do not fill, and a `/SMask` that cannot be reconciled with its picture (a JPEG keeps its own bytes, so its mask is named, not folded in). DOCX is now read beyond the body: a picture inside a header or footer a section defines is sighted at that part and role (`word/header1.xml`, `default_header`), while a section that links its header to the previous one owns no definition and invents nothing. What DOCX still does not sight: footnotes, endnotes and comments parts, and a legacy VML `v:imagedata` reference, which carries no `a:blip` to follow. Confirm whether Phase 12B widens any of these. |
| Q31 | Confirming a picture before `/saxla` | RESOLVED (owner, 2026-10-10) | The caption registers intent; `/saxla` stays the only commit boundary. `ReferenceImageService.record_product_picture` authenticates the actor, resolves an existing product (never creates one), pre-checks the picture's content hash against the active user confirmations and writes exactly one `pending_product_image_confirmations` row against the OPEN session item — no bytes copied, no `ImageAsset`, no relation, and the Azerbaijani reply names both exits (`/saxla` completes, `/cancel` discards). `IngestionSessionService.commit` promotes the queued claims inside its own transaction (content copy → provenance → relation → audit → `LINKED`); a conflict or unreadable bytes found there raise `ReferenceImageSaveDenied`, so the whole save rolls back instead of storing the file and silently dropping the confirmation the user asked for (§23.7). `/cancel` and expiry resolve the row to `CANCELLED` and delete the staged upload, while a relation already committed survives a later unrelated cancel. | Q32 | What counts as a naming caption | RESOLVED (owner, 2026-10-10) | The vocabulary is an **instruction that binds**, not a mention. `business/reference_confirmation.py` reads a caption as a confirmation only when all four hold: an explicit save/link verb closes it — `saxla`, `yadda saxla` or `bağla`, where trailing marks that are not letters (`!`, `.`, an emoji) do not undo a closed phrase while `saxlama`, `saxlamaq`, `saxlanılsın` and `bağlama` keep letters after the verb and so do not close it; exactly one distinct product code appears after canonical normalization, so `KA-45` and `ka45` are one product while `KA45` and `KA46` are two; that code is *bound* to the picture, either by an Azerbaijani naming copula attached (`KA45-dir`, the clipped `KA45-dı`, the unhyphenated `KA45dır`) or standing as its own word (`KA45 dır`), or by the word naming the picture or the product immediately after it (`KA45 şəklini`, `KA45 məhsuluna`, `KA45 referans`, `KA45 üçün`) — matched as a prefix, because Azerbaijani folds case endings into the word, so `şəkli`, `şəkilini` and `şəklidir` all count; and nothing cancels the reading — a `deyil` anywhere denies it, and a question mark anywhere means the user was asking which product the picture shows. So each of the owner's five forms confirms (`Bu KA45-dir, yadda saxla`, `KA45 şəklini yadda saxla`, `Bu şəkli KA45 məhsuluna bağla`, `KA45 üçün referans şəkil kimi saxla`, `Bu KA45 məhsulunun şəklidir, yadda saxla`), while `Bu KA45-dir` and `KA45 şəklini göndərdim` carry no instruction, `Bu məhsul KA45, yadda saxla` and `KA45 anbarda var, yadda saxla` carry an instruction but no binding (a bare code in a sentence is a mention, and a mention is not consent — invariant 1), `Bu KA45-dir deyil, yadda saxla` is denied, `KA45 nədir, yadda saxla?` is a question, `KA45 şəklini yadda saxlama` and `Bu şəkli KA45 məhsuluna bağlama` negate the verb, and `Bu şəkli KA45 və KA46 üçün bağla` names two products — all of these write nothing. A digit is still required, because otherwise an ordinary word becomes an identity claim, and identity stays strict: `KA45-in şəklini yadda saxla` normalizes to `KA45IN`, which is a different code rather than a spelling of `KA45`, so the registry answers "no such product" and the parser guesses nothing. Photos only: a document caption carrying an instruction still reaches the service, which finds no picture in that message and refuses — nothing is inferred from a document. |
