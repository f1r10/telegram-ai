## 0. The measurement problem, stated first

### 0.1 What can be measured today

Nothing on the axes the owner asked about. The reason is structural, not procedural:

- The evaluation corpus is **code-generated text**, not binary files —
  [corpus.py](file:///c:/Users/User/Downloads/ai_assistand/telegram-ai/tests/evaluation/corpus.py#L1-L12):
  *"The corpus is generated by code, never committed as binaries (S2 rule 4). Every entry carries
  the text an ingestion pipeline would extract."*
- Measured coverage (run offline today): `{'pdf': 22, 'docx': 6, 'xlsx': 5, 'txt': 7, 'images': 10,
  'scanned_documents': 5, 'contracts_and_invoices': 7, 'languages': 4, ...}` — **40 documents,
  10 images**, zero of them real bytes with real pixels.
- `docs/PHASE12B-BENCHMARK.md` states the same thing about the OCR side: *"No OCR engine, trained
  model, benchmark score, or accuracy threshold has yet been selected or demonstrated by these
  fixture-only tests."*

So today the only honest values in the tables below are **capability** verdicts (present / absent)
and **licence / dependency** verdicts. Accuracy, latency and memory are **estimates or upstream
claims** until a real corpus exists.

### 0.2 What cannot be measured without a decision from the owner

Benchmarking requires one of:

1. **Deterministically generated binary fixtures at test time** (a PDF/DOCX/XLSX/PNG written by
   code into a temp dir, from the existing synthetic text), keeping the repo binary-free; and/or
2. **An owner-supplied private labelled set** (the only way to measure real Azerbaijani/Russian OCR
   accuracy, matching how `evaluate_docling.py` and `benchmark_ocr.py` are already designed).

Option 1 gives *parser mechanics* numbers (does it extract the text? does it recover a 3×4 table?
does a multi-column page keep order?). Option 2 gives *recognition quality* numbers. Both are
needed; neither exists yet. This is open question #1 in the audit.

### 0.3 The harnesses that already exist (extend, do not replace)

| Harness | File | What it measures | Output contract |
| --- | --- | --- | --- |
| Docling vs native PDF | [evaluate_docling.py](file:///c:/Users/User/Downloads/ai_assistand/telegram-ai/src/office_assistant/scripts/evaluate_docling.py) | **phrase recall** — `native_phrase_recall`, `docling_phrase_recall` over a private label list | JSON: `{"status": "EVALUATED"\| "DRY_RUN"\| "UNAVAILABLE", "truth_sha256", ...}`, `--evaluate` opt-in |
| OCR code extraction | [benchmark_ocr.py](file:///c:/Users/User/Downloads/ai_assistand/telegram-ai/src/office_assistant/scripts/benchmark_ocr.py) | code **precision / recall / F1**, exact-set accuracy, image hit rate, false-alarm rate, **per scenario** | schema-versioned JSON, `--output` optional |
| OCR prediction generation | [run_local_ocr.py](file:///c:/Users/User/Downloads/ai_assistand/telegram-ai/src/office_assistant/scripts/run_local_ocr.py) | produces predictions with local Tesseract | JSONL |
| Single-image probe | [diagnose_image_ocr.py](file:///c:/Users/User/Downloads/ai_assistand/telegram-ai/src/office_assistant/scripts/diagnose_image_ocr.py) | OCR → index → retrieval for one file | human-readable |

Both scoring harnesses are already **privacy-preserving by construction**: `evaluate_docling.py`
never emits the private text (`"Human verified expected text is never copied into result output"`,
line 46) and prints only a `truth_sha256`; `benchmark_ocr.py` refuses per-image labels in output.
Phase 2 must preserve that property, not rebuild it.

- **ADR 0007 is not a permanent verdict.** It records that PyMuPDF was dropped *to avoid AGPL* and

  owner buys a licence.
- **poppler is GPL-2.0+ but is used as a separate process**, not linked — the current OCR path
  already invokes `pdftoppm` as a subprocess, which is the standard GPL-avoidance distance.

## 3. Comparison on the ten required axes

Legend: **YES** / **PARTIAL** / **NO** = current, repository-verifiable capability · **(est.)** =
estimate · **(upstream)** = vendor/community claim, not reproduced here.

### 3.1 PDF text extraction accuracy

| Candidate | Digitally-born PDF | Notes |
| --- | --- | --- |
| pypdf (incumbent) | PARTIAL | `page.extract_text()`; order is content-stream order; no bbox. Audit §2.2 |
| PyMuPDF | YES (est.) | mature, fast C engine; **AGPL blocker** |
| pdfplumber | YES (est.) | wraps pdfminer.six; preserves per-char x/y ⇒ order can be *reconstructed* rather than guessed |
| Docling | YES (upstream) | layout-model-driven; heavier |

**Recommendation:** native text extraction is **not** the gap. pypdf already extracts text. The gap
is **order and structure** (§3.2/§3.6), which is a modelling problem, not a text-extraction one.

### 3.2 PDF layout and reading order

| Candidate | Multi-column order | bbox / coordinates | Verdict |
| --- | --- | --- | --- |
| pypdf | **NO** — interleaves silently | NO | current source of gap **G7** |
| pdfplumber | PARTIAL (est.) | YES — per char/word/line objects | strongest lightweight option |
| PyMuPDF | YES (est.) | YES (`get_text("dict")`) | AGPL blocker |
| Docling | YES (upstream) | YES — layout model predicts reading order + regions | heaviest; CPU cost (§4) |

This is the axis where the incumbent is **wrong, not merely weak**: a two-column contract PDF yields
an interleaved sentence stream that is indexed and citable as if it were correct (audit gap **G7**).

### 3.3 PDF table extraction

| Candidate | Table structure | Cell coordinates | Notes |
| --- | --- | --- | --- |
| pypdf | **NO** | NO | whole page ⇒ one `page_text` block (parsers.py:158–165) |
| pdfplumber | YES (est.) | YES — `extract_tables()` / `extract_table()`, ruled + text-aligned | pure Python; MIT; **1 maintainer** |
| Docling | YES (upstream) | YES — TableFormer model | needs the ~500 MB model set |
| PyMuPDF | PARTIAL (est.) | YES — `find_tables()` | AGPL blocker |
| Unstructured | PARTIAL | varies by backend | matrix REJECT |

**Recommendation:** this is the single largest functional gap (**G1**). Both pdfplumber and Docling
can close it; which one is decided by the benchmark (§5), not by this document.

### 3.4 Scanned PDF support

The incumbent already has a working, capped path: empty native text ⇒ `requires_ocr` ⇒
`pdftoppm` + Tesseract (`--psm 3`), max 80 pages, 15 s/page, 150 s/document
(audit §2.3). So the question is not *whether* scanned PDFs work — they do — but **how accurately**
and **how expensively**.

| Candidate | Scanned PDF | Cost profile |
| --- | --- | --- |
| Tesseract + pdftoppm (incumbent) | YES | CPU-only, apt-installed, fast per page (est. sub-second to a few seconds/page), accuracy language-dependent |
| PaddleOCR / PP-OCRv5 | YES (upstream) | higher accuracy claims, but a model runtime + downloads |
| RapidOCR (PP-OCRv5 ONNX) | YES (upstream) | same models, ONNX Runtime, lighter than PaddlePaddle |
| Docling (`do_ocr=True`) | YES | currently **disabled** in `evaluate_docling.py` (`pipeline.do_ocr = False`, line 80) |
| Cloud OCR | YES | **rejected** — untrusted document bytes must not leave the process for this purpose (ADR 0017 §2) |

### 3.5 Multilingual OCR accuracy — az / en / ru / tr

**Nothing here is measured.** No accuracy number for any language exists in the repository. What is
verifiable is *configuration*:

| Language | Tesseract pack | Installed today? | Evidence |
| --- | --- | --- | --- |
| English | `tesseract-ocr-eng` | **YES** | Dockerfile:15 |
| Russian | `tesseract-ocr-rus` | **YES** | Dockerfile:15 |
| Azerbaijani | `tesseract-ocr-aze` | **YES** | Dockerfile:15 |
| **Turkish** | `tesseract-ocr-tur` | **NO — not installed** | Dockerfile:15 lists only aze, eng, rus |

The configured OCR language set is `aze+eng+rus` (audit §2.3), validated by the regex
`[a-z]{3}(?:\+[a-z]{3})*\Z`. Two consequences:

1. **Turkish is not supported in the deployed image today** and requires adding
   `tesseract-ocr-tur` — a Dockerfile change, which is Phase-2 implementation, not investigation.
2. ADR 0017 calls local Azerbaijani OCR quality *"weak"* on phone photos. Combining `aze+eng+rus`
   in one pass is a **known accuracy risk**: Tesseract mixes script/language hypotheses and can
   *reduce* per-language accuracy versus a single-language pass. Whether `aze` should run alone for
   Azerbaijani pages is a measurable question (§5), not an assumption.

**Honest position:** arabic-script-free, Latin+Cyrillic content is Tesseract's strong suit; the
unmeasured risk is specifically **Azerbaijani Latin diacritics (ə, ı, ğ, ş, ç, ö, ü)** and
**code-like strings** (the existing `benchmark_ocr.py` measures exactly this, on product codes).

### 3.6 Excel multi-sheet understanding

| Candidate | Multi-sheet | Formulas | Cached values | Merged cells | Cross-sheet |
| --- | --- | --- | --- | --- | --- |
| **openpyxl (incumbent)** | YES — `for sheet in workbook.worksheets` (parsers.py:588) | YES — formula **strings** kept | **NO** — `data_only=False` (parsers.py:584) | PARTIAL — `merged_cells` API exists, not used | **NO** |
| openpyxl `data_only=True` (2nd pass) | YES | **NO** — formula replaced by cached value | YES — *if* Excel cached it | same | **NO** |
| pandas + openpyxl | YES | NO | YES | NO | NO |
| calamine | YES | YES | YES | PARTIAL | NO |

**Key finding:** no candidate provides "cross-sheet reasoning" as a feature — that is *our* job
(gap **G6**), built on top of whatever reader we keep. And openpyxl already exposes both views: a
**second `data_only=True` pass** would give cached values *without changing the primary read*, so the
existing "preserve the formula verbatim" behaviour (parsers.py:584, deliberate) survives while
computed values become available as a separate, labelled fact. That is a two-pass design, not a
library swap. See [ARCHITECTURE.md](file:///c:/Users/User/Downloads/ai_assistand/telegram-ai/docs/phase-2/ARCHITECTURE.md) §4.

| Candidate | Headings | Heading **level** | Lists / numbering | Table cell coords | Metadata | Embedded images |
| --- | --- | --- | --- | --- | --- | --- |
| **python-docx (incumbent)** | PARTIAL — style-name prefix only (parsers.py:437) | **NO** | **NO** — lists are ordinary paragraphs | PARTIAL — joined string + row index | **NO** — `metadata={}` (parsers.py:470) | YES — body/header/footer (parsers.py:505–575) |

### 3.8 Memory consumption and processing speed

**All figures in this table are estimates or upstream claims. None is measured here.** The
methodology that would replace them is in §5.

| Candidate | Resident/runtime memory | Per-document work | Install size (est.) |
| --- | --- | --- | --- |
| pypdf | small (pure Python, streamed) | fast (est.) | ~0 |
| pdfplumber | moderate (builds full char/layout objects — memory grows with page complexity) | slower than pypdf (est.), pure Python | small |
| python-docx / openpyxl | small–moderate | fast for typical office files | small |
| Tesseract + poppler | moderate, per raster page; already capped (16 MiB raster, 15 s/page) | CPU-bound, seconds/page (est.) | apt packages |
| **Docling** | **~200–500 MB RAM per document** (report), plus model residency | ~0.5–2 s simple, **10–30 s complex/scanned** (reports) | **~500 MB model download** + torch/ONNX |
| PaddleOCR / RapidOCR | ONNX path lower than PaddlePaddle; model-dependent | seconds/image (est.) | tens–hundreds of MB models |
| EasyOCR | **PyTorch** resident (hundreds of MB) | slow on CPU (est.) | very large |

The decisive number for this project is Docling's: a single VM running `app`, `worker`, `postgres`,
`qdrant` and `searxng` (AGENTS.md) cannot absorb a ~500 MB model download plus coupling of hundreds
of MB per concurrent document without an explicit capacity decision. See
[DEPENDENCY_REVIEW.md](file:///c:/Users/User/Downloads/ai_assistand/telegram-ai/docs/phase-2/DEPENDENCY_REVIEW.md) §5.

### 3.9 CPU compatibility

- **This project is CPU-only by design.** No CUDA assumption appears in the Dockerfile or compose.
- pypdf / pdfplumber / python-docx / openpyxl: pure Python or small wheels ⇒ trivially CPU-compatible.
- Tesseract / poppler: CPU-native.
- **Docling on CPU is the slow path** (its speed claims assume GPU). Acceptable only as an opt-in,
  bounded, offline operation.
- PaddleOCR/RapidOCR: ONNX Runtime CPU is the practical option; PaddlePaddle CPU wheels exist but are
  heavier and historically more fragile to install.

### 3.10 Installation complexity and dependency conflicts

| Candidate | Install | Conflict risk against `uv.lock` |
| --- | --- | --- |
| pdfplumber | `+ pdfplumber` (+ `pdfminer.six`) | LOW — pure Python, MIT, no torch |
| and maintainers | 1 maintainer (bus-factor risk; MIT mitigates)* | LOW |
| Docling | `+ docling` (+ torch or ONNX, transformers, model artifacts) | **HIGH** — large transitive tree, version pressure on `pydantic`, `numpy`, `huggingface-hub`; model download at runtime |
| PaddleOCR | `+ paddleocr` (+ paddlepaddle) | **HIGH** |
| RapidOCR | `+ rapidocr-onnxruntime` (+ onnxruntime) | MEDIUM |
| EasyOCR | `+ easyocr` (+ torch) | **HIGH** |
| Unstructured / Tika | `+ unstructured[all]` / JVM | **REJECT** (matrix) |

*pdfplumber/pdfminer.six are MIT and widely vendored, which mitigates — but does not remove — the
single-maintainer risk. It must appear in [DEPENDENCY_REVIEW.md](file:///c:/Users/User/Downloads/ai_assistand/telegram-ai/docs/phase-2/DEPENDENCY_REVIEW.md).

The Dockerfile pins `uv sync --frozen` against a committed `uv.lock`. Any candidate is therefore an
**opt-in dependency group**, never a silent addition to the runtime image, until it has a measured
justification (audit risk **R2**).

## 4. Per-role recommendation (candidate, not yet decided)

These are the **hypotheses the Phase-2 benchmark must confirm or falsify**. They are not a decision.

| Role | Recommended candidate | Why | What could overturn it |
| --- | --- | --- | --- |
| PDF native text | **keep pypdf** | text extraction is not the gap; BSD-3; already installed | a measured recall failure on real PDFs |

| Scanned PDF / OCR engine | **keep Tesseract**, add an `OCRProvider` seam | it works and is already capped; the seam is what is missing (**G2**) | PaddleOCR/RapidOCR measurably better on az/ru, at acceptable cost |

| OCR text → number | **not an OCR-engine change** | low-confidence OCR lines need a *confidence + human-confirmation* path, not a different engine (**G3**) | — |

**Explicitly not recommended for adoption:** PyMuPDF (AGPL), EasyOCR (torch), Apache Tika (JVM),
Unstructured (matrix REJECT), any cloud OCR (data residency).

## 7. Summary

1. **There is no measured benchmark, and it is not a missing procedure — it is a missing corpus.**
   The harnesses exist and are privacy-safe; they need real bytes.
2. **Native PDF text is not the problem. PDF table structure and reading order are** (gaps G1/G7),
   and reading order is a correctness bug, not a quality gap.
3. **The Windows are role-specific:** pdfplumber is the plausible lightweight win for PDF
   structure; Docling is the accuracy ceiling but carries a ~500 MB + hundreds-of-MB-RAM tax that
   must be an explicit owner decision.
4. **Turkish OCR is not available in the deployed image**, and the combined `aze+eng+rus` pass is
   an unmeasured accuracy risk — not a proven configuration.
5. **Most of the Excel and Word gap is reachable without any new dependency** (a second
   `data_only=True` read; reading `outlineLvl`/`numPr`/`core_properties`).
6. **The missing architectural piece is the seam, not the engine** (gap **G2**): an `OCRProvider`
   interface, so engines can be benchmarked and swapped without editing production services.
